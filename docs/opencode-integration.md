# OpenCode: приём запросов с VPS

## Выбранная схема

```text
Telegram → bot/queue на VPS ← исходящий HTTPS poll от PC connector
                                      ↓ localhost HTTP + Basic Auth
                               opencode serve (ПК)
                                      ↓
                             DeepSeek OpenCode session
```

VPS не подключается к ПК напрямую. Connector работает на ПК и сам забирает задания у VPS. OpenCode API доступен только локально. DeepSeek API key используется OpenCode для модели, но не участвует в сетевой доставке запросов.

## OpenCode server на ПК

OpenCode предоставляет headless HTTP server (`opencode serve`) с OpenAPI-описанием и API сессий. Для постоянной интеграции поднимать отдельный серверный процесс, а не подключаться к случайному порту интерактивного TUI.

Предлагаемая настройка:

- Запускать от той же Windows-учётной записи, в которой OpenCode видит профиль провайдера, проектные инструкции, память и доступ к календарному MCP.
- Запускать с рабочим каталогом HR-проекта, фиксированным портом, hostname `127.0.0.1` и паролем `OPENCODE_SERVER_PASSWORD`.
- Держать OpenCode API на localhost и защищать его Basic Auth (пользователь `opencode` по умолчанию). Не настраивать публичный reverse proxy, CORS или проброс порта для этого API.
- Запускать сервер при старте ПК через Windows Task Scheduler или существующий supervisor и контролировать health endpoint.
- Сохранять постоянный ID одной OpenCode-сессии для единственного специалиста на ПК. Создать session через API при первом запуске, затем повторно использовать. Контекст сессии помогает диалогу, но структурированная память HR-задач должна храниться отдельно в устойчивых данных проекта.
- Использовать отдельный primary agent `hr-assistant` и явно передавать его ID в OpenCode API. Загрузить `docs/deepseek-agent-instructions.md` через `instructions` OpenCode config или включить его содержимое в инструкции выделенного агента. Один лишь файл в репозитории бота автоматически агенту не попадёт.

## Учёт частых обновлений OpenCode

OpenCode не фиксируется в проекте на конкретную версию: установка и обновление выполняются отдельно на ПК. Connector читает текущую версию из `/global/health` при старте и с интервалом `OPENCODE_CHECK_INTERVAL_SECONDS`. При новой версии он заново читает `/doc`, проверяет используемый session message endpoint и наличие агента `hr-assistant`. При ошибке проверки worker сообщает relay о нездоровом состоянии и не забирает новые задания. Версия пишется в heartbeat и журнал.

После обновления OpenCode следует проверить официальные release notes и API на тестовом запросе. Автопроверка обнаруживает изменения в объявленном контракте, но не гарантирует неизменность семантики всех полей. Если контракт изменился, адаптировать connector по актуальным docs и OpenAPI, а не обходить проверку. Не запускать параллельные connector процессы с одной сессией.

## Connector на ПК

- Connector — самостоятельный фоновый процесс проекта. Он выполняет только transport/retry и вызов OpenCode; не хранит бизнес-задачи и не принимает HR-решений.
- Connector первым устанавливает HTTPS-соединение с узким VPS relay API и запрашивает следующий job (длинный polling). Не нужны открытые входящие порты, VPN или webhook на ПК.
- VPS job содержит случайный `correlation_id`, идентификаторы разрешённого Telegram chat/message, исходный текст, время приёма и lease. Сервер проверяет единственный настроенный Telegram ID до постановки задания.
- После получения job connector вызывает `POST /session/{session_id}/message` на локальном OpenCode API. Этот endpoint отправляет сообщение выбранной сессии и ждёт результат. Для MVP запросы в одну сессию обрабатывать последовательно.
- Connector извлекает только финальный текст ассистента из результата OpenCode, скрывает reasoning/tool internals и отправляет результат на VPS с тем же `correlation_id`. VPS-bot редактирует исходное «Размышление».
- Lease/heartbeat и идемпотентность защищают от повторов при обрыве. Если OpenCode завершил задачу, но connector потерял ответ, использовать correlation ID и историю OpenCode для восстановления, чтобы не запускать мутацию повторно.
- При недоступности OpenCode connector сообщает relay ошибку для пользователя, а не оставляет «Размышление» бесконечно.

## Отдельный канал напоминаний

OpenCode server сам по себе — HTTP/API для сессий, не планировщик по времени. Агент записывает задачи/напоминания в своё долговременное хранилище. На ПК понадобится пробуждение агента в нужное время: агентский scheduler или companion runtime отправляет в выделенную OpenCode-сессию запрос проверить наступившие напоминания и затем просит VPS relay доставить сообщение. Этот runtime не должен копировать или самостоятельно менять бизнес-память задач.

При перезапуске ПК агент восстанавливает ближайшие напоминания из долговременной памяти; политика пропущенных сроков описана в `docs/deepseek-agent-instructions.md` и ещё должна быть определена.

## Ограничения инструментов

- DeepSeek API key хранится в профиле OpenCode на ПК и используется только для вызова модели.
- OpenCode обычно разрешает большинство инструментов без подтверждения. Для Telegram-агента явно задать permissions: запретить `bash`, `edit/write/patch`, запуск subagent и все неиспользуемые средства; разрешить только чтение нужных HR-файлов и узкие tools для задач, календаря и отправки Telegram-уведомления.
- Долговременную память реализовать за отдельным ограниченным MCP/tool интерфейсом (`task_create`, `task_list`, `task_update`, `reminder_list_due` и аналогичные). Хранилище находится на ПК; инструмент проверяет схему, owner/user ID, время и idempotency. Не давать модели произвольное shell-управление этим хранилищем.
- Google Calendar подключается как локальный MCP/tool в OpenCode (если подходящий инструмент уже есть — использовать его; иначе добавить ограниченный wrapper). Предоставить только чтение/занятость и `events.insert`; update/delete tools не подключать.
- Для доставки напоминаний дать агенту отдельный узкий MCP/tool, который передаёт relay команду в очередь VPS. Он принимает только разрешённый chat ID, текст и idempotency ID, не произвольный URL или Telegram API method.
- Не проксировать из Telegram универсальный OpenCode API: там есть возможности управлять сессиями, инструментами и shell. VPS должен видеть только узкий relay API, а локальный OpenCode API — только connector на localhost.
- Текст пользователя и результат модели считать данными; валидировать действия и авторизацию инструментами. Не отправлять reasoning, API keys, OAuth tokens или внутренние сведения в Telegram.

## Официальная документация OpenCode

- [Server](https://docs.opencode.ai/docs/server/) — `opencode serve`, default hostname/port, Basic Auth и API сессий.
- [SDK](https://docs.opencode.ai/docs/sdk/) — typed client и методы session.
- [MCP servers](https://docs.opencode.ai/docs/mcp-servers/) — local/remote MCP servers, auth и настройка tools.
- [Permissions](https://docs.opencode.ai/docs/permissions/) — права OpenCode по умолчанию и ограничения инструментов для отдельного агента.
- [Config](https://docs.opencode.ai/docs/config/) — подключение файлов инструкций через `instructions`.
- [Providers](https://docs.opencode.ai/docs/providers/) — подключение DeepSeek provider/API key; данные auth хранятся в профиле OpenCode.

## Реализованный транспортный каркас

`relay_bot/` содержит Telegram long polling с allowlist одного private user, SQLite очередь и API для connector. `connector/` подключается к `opencode serve` на localhost, подтверждает контракт API при изменении версии и последовательно отправляет пользовательские запросы в выделенную сессию. Relay ограничивает срок ожидания неподключённого агента; после неопределённого результата запрос не переигрывается автоматически, чтобы избежать двойной календарной операции.

Память задач, Google Calendar tools и scheduler агента пока не реализованы. Endpoint приёма уведомлений на VPS существует, но нужен ограниченный OpenCode MCP/tool adapter для постановки напоминаний. Не считать календарь или напоминания интегрированными до отдельной реализации и проверки.
