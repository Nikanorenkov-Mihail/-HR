# Предлагаемая архитектура

## Источник истины

DeepSeek-агент на постоянно включённом ПК отвечает за понимание запроса, контекст, долговременную память, HR-задачи, сроки, напоминания и действия в Google Calendar. VPS-бот не реализует эту бизнес-логику: он переносит сообщения и выполняет отправку/редактирование сообщений Telegram.

## Компоненты

- **Telegram adapter на VPS** — long polling, allowlist одного Telegram ID, сообщение «Размышление», редактирование финального ответа, доставка reminder-сообщений.
- **Relay API / очередь на VPS** — краткосрочно хранит запросы от Telegram и ответы/команды уведомлений от connector. У каждой операции есть `correlation_id` или `operation_id`; обработанные задания получают подтверждение, повторы идемпотентны.
- **PC connector** — постоянно работающий процесс на ПК, который сам опрашивает VPS по аутентифицированному HTTPS, получает задания, передаёт их в локальный OpenCode API и возвращает результат. Не публиковать локальный интерфейс OpenCode в публичную сеть.
- **OpenCode server** — отдельный headless `opencode serve` на ПК, привязанный к `127.0.0.1` и защищённый Basic Auth; агентские запросы отправляются в выделенную сессию через OpenCode HTTP API.
- **DeepSeek agent** — OpenCode с настроенным DeepSeek provider и инструкциями из `docs/deepseek-agent-instructions.md`; владеет долговременным хранилищем задач/памяти, календарной интеграцией и правилами напоминаний.
- **Google Calendar API на ПК агента** — агентские credentials/OAuth; в первой версии доступны только операции чтения и создания событий.
- **Техническая relay-БД на VPS** — только необходимые данные для маршрутизации и повторной доставки: correlation ID, chat/message ID, статус, дедлайн и idempotency key. Не является памятью пользователя.

## Размещение

В `Bot_lanch_tz` используется Docker Compose на VPS, `restart: unless-stopped`, long polling Telegram и volume для постоянных данных. Новый бот следует строить по этому шаблону; детали текущего VPS и его сетевой доступности ещё нужно подтвердить.

Предпочтительный канал для VPS↔ПК — connector на ПК, который держит исходящее защищённое соединение и забирает задания. Тогда не требуется входящий порт к ПК. Альтернатива — уже настроенная частная сеть/VPN. Прямой публичный доступ к локальному агенту не использовать.

## Приём запросов через OpenCode

Выбранный путь — **VPS job queue → PC connector → OpenCode local HTTP API**:

1. Telegram-бот кладёт сообщение в техническую очередь VPS и отправляет «Размышление».
2. Connector на ПК первым устанавливает соединение к VPS, забирает job с correlation ID и продлевает lease при долгой обработке.
3. Connector вызывает `POST /session/:id/message` на `http://127.0.0.1:<port>` для закреплённой HR-сессии OpenCode. Endpoint ожидает завершения ответа и возвращает сообщение с частями.
4. Connector отправляет финальный текст/статус на VPS с тем же ID; бот редактирует исходное сообщение.

Для MVP использовать один выделенный OpenCode project/session для единственного специалиста и последовательную обработку запросов. ID сессии сохранять локально на ПК; бизнес-память задач сохранять отдельно от истории OpenCode. При переходе на несколько сотрудников разделять сессии и данные пользователей.

Локальный сервер запускать headless с фиксированным портом и `--hostname 127.0.0.1`; задать `OPENCODE_SERVER_PASSWORD`. Connector подключается к нему по HTTP Basic Auth. На VPS доступны только наши узкие endpoints очереди/результата; нельзя делать reverse proxy к OpenCode API целиком. Для длинных задач connector должен держать job lease и корректно восстанавливать обработку после перезапуска.

## DeepSeek API key и связь с агентом

API key DeepSeek Platform — это bearer credential для запросов к облачной модели. Он позволяет боту на VPS вызывать DeepSeek API, но не подключает бот к запущенному на ПК агенту, не открывает локальные файлы и не переносит память/инструменты агента. Tool/function calling тоже требует клиентского кода: модель возвращает вызов инструмента, а клиентская программа выполняет его и передаёт результат модели.

Если сохраняем выбранную схему с агентом на ПК, bot↔agent соединение всё равно нужно: PC connector забирает с VPS сообщения и возвращает ответ. API key может отдельно использоваться самим агентом на ПК как backend-модели, если это действительно его текущая конфигурация. Если же бот напрямую вызывает DeepSeek API на VPS, это уже альтернативная архитектура без текущего локального агента; доступ к Google Calendar и памяти тогда надо реализовать/перенести отдельно.

## Обычный запрос и «Размышление»

`Telegram update → allowlist → отправить «Размышление» → создать relay-job → PC connector → DeepSeek agent → результат через relay → edit исходного сообщения`

Бот сохраняет связь `correlation_id → chat_id/message_id`, чтобы отредактировать правильное сообщение. При ошибке или таймауте агента редактирует его понятным сообщением об ошибке. Бизнес-контекст не записывает.

## Напоминание

`Пользователь → Telegram relay → агент разбирает просьбу → агент сохраняет задачу/время → агентский scheduler → команда уведомления через relay → бот отправляет в разрешённый чат`

Планировщик и источник расписания находятся на ПК агента. Команда отправки содержит allowlisted chat ID, текст уведомления, operation ID и время отправки. Бот проверяет источник/подлинность команды и идемпотентность, но не вычисляет срок и не решает, пора ли напоминать.

## Google Calendar и пересечения

1. Агент уточняет название, дату, время, длительность, часовой пояс и календарь, если данных не хватает.
2. Через Google Calendar API агент читает события/занятость за нужный временной интервал.
3. Сравнивает полуоткрытые интервалы `[start, end)`; события, заканчивающиеся ровно в момент начала нового, не пересекаются. Учитывает часовой пояс и длительность.
4. Если найдено пересечение, сообщает занятые интервалы и спрашивает пользователя: создать исходный вариант несмотря на занятость или изменить время/параметры. До решения не вызывает создание события.
5. Если пользователь явно выбрал «создать несмотря на конфликт», агент повторно читает календарь и создаёт событие. Если выбрал другой вариант, проверяет новый интервал.
6. После создания агент сообщает подтверждённые детали и сохраняет Google event ID в своей памяти, если он нужен для последующих напоминаний.

VPS-бот не получает Google OAuth credentials. Предоставить агенту только операции `list/get/freebusy` и `insert`; не давать инструменты `update/delete`. Google scope для создания событий шире, чем только insert, поэтому ограничение операций также должно быть enforced на уровне wrapper/tools, а секреты должны оставаться на ПК.

## Надёжность и доступ

- Проверять Telegram user/chat ID до передачи текста агенту; пока один HR-специалист.
- Дедуплицировать Telegram updates, relay jobs, ответы и reminder delivery по стабильным ID. Повторно доставляемая команда не должна повторно создавать событие или сообщение.
- Connector должен возобновлять соединение после перезапуска/обрыва; relay должен сообщать о просроченных или неподтверждённых запросах.
- Секреты и персональные данные не писать в обычные логи. Google refresh token хранить только на ПК агента.
- По умолчанию использовать `Europe/Moscow`, если пользователь не указал другой часовой пояс; все времена хранить однозначно с timezone.
