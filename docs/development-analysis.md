# Анализ разработки

## Зафиксированные решения

- Telegram-бот работает на VPS по образцу `Bot_lanch_tz`.
- В первой версии есть один пользователь — HR-специалист; бот ограничивает доступ его Telegram ID.
- Бот — relay: отправляет «Размышление», пересылает запрос, редактирует ответ агента и доставляет агентские напоминания. Задачи/память и Google Calendar он не меняет.
- DeepSeek-агент работает на постоянно включённом ПК и является источником истины для памяти, задач, напоминаний и календарных операций.
- Агент читает календарь и создаёт новые события. При пересечении по времени предупреждает и просит выбрать: создать несмотря на занятость или изменить запрос. До выбора конфликтующее событие не создаёт.
- Позже можно добавить других сотрудников; контекст, доступ и задачи должны быть разделены по пользователю.

## Референсы

### Проект «Ассистент»

В папке `Ассистент` есть база задач JSON с полезной моделью: ID, название, статус, приоритет, срок, заметки, решения, блокеры и следующий шаг. Использовать эти поля как образец долговременной памяти агента. Сами записи не копировать — они содержат рабочие и клиентские данные.

### Проект `Bot_lanch_tz`

В локальном проекте `Bot_lanch_tz` обнаружены:

- Python + aiogram; Telegram updates получают через long polling (`dp.start_polling(bot)`).
- Docker Compose для VPS, автоматический перезапуск `unless-stopped`, переменные через `.env`, постоянный `./data` volume.
- SQLite для прикладных данных и allowlist администраторов по Telegram ID.
- Отдельный async HTTP-клиент к настраиваемому VLM API.

Для нового бота можно повторить стиль VPS-развёртывания, long polling и ограничения по Telegram ID. Не копировать `.env`, ключи, базу, данные пользователей или предметную логику. VLM endpoint в референсе не подтверждает, что локальный агент принимает совместимые HTTP-запросы. Версии библиотек при начале реализации сверить заново.

## Архитектура, соответствующая решениям

1. На VPS остаются Telegram-бот, технический relay/API и очередь сообщений с краткосрочным техническим состоянием.
2. На ПК работает connector, который сам устанавливает аутентифицированное исходящее соединение к VPS, передаёт запрос локальному агенту и возвращает ответ по correlation ID. Публичный порт к агенту не открывается.
3. Connector вызывает локальный OpenCode `opencode serve` на `127.0.0.1` через HTTP Basic Auth и отправляет сообщение в закреплённую session через `POST /session/:id/message`.
4. На ПК агент держит постоянную память задач и напоминаний, подключает Google Calendar и планирует уведомления.
5. Для чтения и создания событий агент проверяет соответствующий интервал перед созданием. При конфликте возвращает в Telegram предупреждение и ждёт выбора; после подтверждения создания проверяет календарь повторно.
6. Когда наступает срок напоминания, агент отправляет relay команду доставки. Бот проверяет allowlist/idempotency и отправляет сообщение в Telegram.

## Проверка DeepSeek API key

API key DeepSeek Platform **не является ключом связи с агентом на ПК**. Он используется как Bearer credential при запросе облачной модели по `https://api.deepseek.com`. Если поставить этот ключ в VPS-бот, бот сможет получать ответы облачной модели, но не получит локальную память, файлы или Google Calendar агента. DeepSeek tool calls тоже выполняет клиентский код, а не модель сама.

Поэтому для выбранной схемы нужен отдельный PC connector/relay. Если локальный агент сам использует DeepSeek Platform как модельный backend, ключ может храниться на ПК и вызывать модель оттуда; доставка запросов с VPS всё равно требует connector. Вызов API непосредственно из бота — отдельный вариант архитектуры, который заменил бы текущий агентский процесс.

## Важные ограничения

- Бот не хранит бизнес-память и не принимает решений о сроках или календаре. Техническая очередь может временно держать текст запроса для передачи и retry; после подтверждения агентом его следует удалять согласно политике хранения.
- Google OAuth-токены принадлежат среде агента на ПК и не попадают на VPS. Calendar scopes могут дать более широкие возможности, чем нужен продукту: разрешённые операции `read` и `insert` надо ограничить также на уровне подключённых tools/wrapper, без `update/delete`.
- Уведомления надёжно сработают только если агентский scheduler доступен. ПК обозначен постоянно включённым, но политика для выключения/пропущенных напоминаний ещё нужна.
- Не создавать календарные события из одной лишь просьбы «напомнить о встрече»: по формулировке пользователя определить, нужно ли только внутреннее напоминание или событие Calendar; при сомнении спросить.
- HR-переписка может содержать персональные данные: ограничивать доступ одним ID, сокращать содержание логов и не сохранять полные стенограммы без установленной необходимости.

## Что уточнить перед реализацией

1. Какая версия OpenCode установлена, где находится его рабочий HR-проект и под какой Windows-учётной записью он должен запускаться постоянно?
2. Какой HTTPS URL будет доступен connector-у на VPS и где хранить отдельный relay-token? Нужен только исходящий доступ с ПК.
3. Настроен ли DeepSeek provider/API key в OpenCode на этом ПК?
4. Подключён ли Google Calendar к OpenCode (MCP/tool) и какой календарь использовать, если их несколько?
5. Что делать с напоминаниями, срок которых прошёл пока агент/ПК был недоступен: отправлять после запуска, пропускать или запрашивать решение?
6. Подтвердить часовой пояс по умолчанию (`Europe/Moscow` предлагается из текущих настроек).

## Официальные технические источники

- [Telegram Bot API](https://core.telegram.org/bots/api) — `getUpdates`, `sendMessage`, `editMessageText`.
- [Google Calendar API scopes](https://developers.google.com/workspace/calendar/api/auth) — минимально необходимые OAuth-разрешения; `calendar.events.owned` поддерживает чтение/создание/изменение/удаление в календарях владельца.
- [Google Calendar Freebusy query](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query) — проверка занятости за временной интервал.
- [Google Calendar Events: insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) — создание события.
- [DeepSeek API: авторизация](https://api-docs.deepseek.com/api/deepseek-api/) и [tool calls](https://api-docs.deepseek.com/guides/tool_calls/) — ключ авторизует запрос модели; функции выполняет клиентское приложение.
- [OpenCode Server](https://docs.opencode.ai/docs/server/) и [Providers](https://docs.opencode.ai/docs/providers/) — локальный HTTP API и настройка DeepSeek provider.
- [OpenCode Permissions](https://docs.opencode.ai/docs/permissions/) и [MCP servers](https://docs.opencode.ai/docs/mcp-servers/) — ограничение инструментов и подключение локальных HR/Calendar tools.
